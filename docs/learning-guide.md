# 把这个项目变成你能讲清楚的作品

初版代码由 AI 辅助创建。接下来建议亲自完成下面三件事，并保留调试记录；理解和维护它之后，再据实整理个人经历。

## 1. 从命令行追一次完整请求

从 `cli.py` 进入 `research.py`，找到 GitHub 返回的 issue/PR 混合列表如何被过滤，候选如何排序，为什么列表达到上限时不能写“没有重复”。用 `--format json` 检查生成的来源和风险字段。

## 2. 自己补一个真实失败案例

选一个你看得懂的 issue，人工查看规则、评论和 PR。工具判断不准确时先解释原因，然后用虚构最小输入写失败测试，再修改实现。例如：中文认领表达漏报，或仅交叉引用的 PR 被过度暂缓。

## 3. 完成一次真实模型评测

配置自己的模型，在小样本上检查 AI 是否编造文件路径、误读贡献规则或给出无证据的确定结论。记录一次正确例和一次失败例、token 用量与耗时。不要把“JSON 格式正确”当成“分析正确”。

## 可以练习回答的问题

- 为什么事实采集使用确定性代码，分析才交给 LLM？
- 模型引用了真实链接，为什么仍可能产生幻觉？
- 为什么有相关 PR 不一定等于有人在解决同一问题？
- 为什么使用异步任务，任务上限与历史保留解决了什么？
- 面对权限不足、分页截断和 API 限流，如何保证报告不误导用户？

先把一个改进从“观察 → 复现 → 测试 → 修改 → 验证”完整走通，再扩大项目范围。
