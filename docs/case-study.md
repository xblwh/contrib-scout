# 一次真实使用记录：调研如何推动工具改进

**已完成：使用工具、修改、自审、测试、提交 PR、CI 通过、合并至自有项目。第三方社区接受贡献的案例尚未建立。**

这份记录来自真实开发过程，手工去除了身份信息和贡献定位信息。它不是虚构演示，也不是独立维护者采纳的证明。启动本地服务后，从首页「阅读真实使用记录」进入完整流程页面（`/case-study`）。

## 实际过程

1. **调研。** 以 Python、TypeScript 为技术栈，对三个公开仓库运行 Contrib Scout，关闭可选模型分析；在本地保留采集返回与报告。
2. **确定问题。** 核对报告和来源，发现候选会混入仅在背景提及技术栈的问题，普通验证引用会干扰关联 PR 判断；阶段检查又发现只含 Python 文件路径的相关问题会被漏选。
3. **修改与自审。** Codex 分开技术、规则与协作状态，细分 PR 引用关系、核实文件入口并补回归。自审修正了过严过滤、漏识别修复意图、弱化部分范围关联等偏差。
4. **验证。** 回放缓存、重新联网核对，运行 Python 与 TypeScript 检查，检查独立安装、网页与手机布局、报告下载。新增来源另行读取，前后对比不是完全相同的时间快照；未据此宣称准确率。
5. **提交与合并。** Codex 提交独立分支和 PR，披露 AI 辅助、验证与限制；远程多版本 Python 和前端 CI 通过后，依照所有者授权合并，并核实主分支 CI 通过。

Contrib Scout 负责只读采集与整理。核对原文、开发、测试、自审、Git 操作和合并由 Codex 执行；所有者提供需求和授权，未进行本次逐行人工复核。工具本身没有自动提交或合并功能。

未运行被调研仓库代码、未确认其贡献许可、未调用真实付费模型。已经发生的自有项目合并不能替代独立社区接受贡献。

## 今后怎样记载对外贡献

完整案例应能逐项追溯：实际使用工具的时点与报告、规则核对、复现、最小修改、验证、提交、维护者反馈、后续修改、最后的合并状态与采纳范围。工具只能归因于它真实参与的环节；在工具参与之前已提交的 PR，不能倒写成工具发现或促成提交。

| 可核实状态                               | 可以使用的表述                         |
| ---------------------------------------- | -------------------------------------- |
| 只有报告                                 | 已完成初步调研                         |
| 本地复现、修改与验证完成                 | 已验证本地修改                         |
| PR 已创建，仍开放                        | 已提交，等待处理                       |
| CI 通过                                  | 自动检查通过，合并状态另记             |
| 维护者提出反馈，尚未合并                 | 协作中；说明反馈和已完成的修订         |
| 对方维护者明确合并，且实际改动范围已核对 | 第三方贡献已合并；仅陈述已采纳范围     |
| 自有项目按授权合并                       | 自有项目改进已合并；说明审核与合并角色 |

## 隐私与可验证性

本案例省略姓名、账号、邮箱、本机路径、精确时间、被调研仓库名、具体贡献编号、可识别的原文引用、个人截图与贡献链接。过程使用概述，未用虚构编号或链接冒充真实证据。

原始报告、PR/CI 状态与公开叙述的对应关系仅保存在本地被忽略的目录；不上传到仓库、发布附件或案例页面，也不把原文整批发送给模型。页面只加载本地静态样式，无远程字体、分析脚本或嵌入。

这使读者无法仅凭本页独立复核原始记录。去除身份字段也不保证不可关联：公开仓库的发布者与既有提交历史仍可能指向作者。这里提供的是内容层面的隐私处理，不承诺完全匿名。

**普通 Markdown / JSON 调研报告仍包含来源链接和摘录，本次没有增加通用自动脱敏功能。** 分享报告前需另行检查正文、链接、截图、文件名与附件；未经明确许可，不为增强案例可信度而公开可追溯到贡献者的证据映射。
