# 开发案例：用调研报告改进候选筛选

实际使用 Contrib Scout 调研公开仓库后，报告暴露出技术匹配与关联 PR 分类的问题。本案例记录问题核对、实现、验证与本项目内合并的过程。

结果为本项目内的改进已合并、CI 通过。采集、实现与复核使用 AI 辅助，验证方式为自动检查和阶段自查，未进行独立评审。这不是第三方社区采纳贡献的案例。

## 从报告到修正

1. **保存基线。** 以 Python、TypeScript 为技术栈，对三个公开仓库运行调研，关闭可选模型分析；保存当时返回与报告用于比较。
2. **核对误判。** 回到问题与 PR 原文，区分普通引用、部分范围关联和解决意图；确认仅在背景提及技术栈的问题，以及只含 Python 文件路径的问题应如何处理。
3. **实现与复核。** 分开展示技术相关性、贡献规则和协作状态，细分引用关系，核实原文文件入口。阶段复核修正过严过滤、漏识别修复声明和弱化部分范围关联的问题，并补充最小回归。
4. **验证。** 回放已有材料、重新联网检查，运行 Python 测试与 TypeScript 检查，验证独立安装、桌面和手机页面、Markdown / JSON 下载。新增来源另行读取，前后比较不是完全相同的时间快照。
5. **提交与合并。** 在独立分支提交改动，PR 记录变更、检查和限制。多版本 Python 与前端 CI 通过后，在本项目内合并，并确认主分支 CI 通过。

Contrib Scout 负责只读采集与报告，开发、测试和 Git 操作在工具之外执行。工具没有自动提交或合并功能。

## 验证范围

实际修正和来源说明见 [evaluation.md](evaluation.md)，回归入口见 [test_actionable.py](../tests/test_actionable.py)。测试通过不构成推荐准确率；文件入口存在不证明根因。本次未运行目标仓库代码、未确认贡献许可、未评估真实模型语义质量。

现场原始材料未作为公开数据集发布；公开测试使用虚构或最小化输入。普通调研报告包含来源链接与摘录，分享前应检查其中的信息。

## 如何记录贡献结果

调研、复现、验证、提交、CI 和合并分别记录；工具仅归因于它真实参与的环节。已提交、检查通过和已合并是不同状态；第三方维护者合并后，成果表述仍应限定于实际采纳范围。不能将工具参与前已提交的贡献写成由工具促成。
