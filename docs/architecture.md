# 设计取舍

## 数据流

```mermaid
flowchart LR
  A[CLI / TypeScript UI] --> B[Python 调研器]
  B --> C[GitHub 只读 API]
  C --> D[带来源的事实快照]
  D --> E[规则筛选与风险标记]
  E --> F[Markdown / JSON / 浏览器报告]
  E --> G[可选 LLM JSON 分析]
  G --> H[编号、字段与来源 ID 校验]
  H --> F
```

调研器与 HTTP/CLI 分离。测试可注入 GitHub 客户端和模型响应，无需网络或付费密钥。浏览器通过任务 ID 查询进度；服务同时执行最多两项任务。

## 为什么先用确定性采集

Issue 状态、assignee 和关联 PR 有可查询的数据来源。把这些事实直接交给模型猜测会增加不必要的不确定性。模型只承担分析和建议，不能改变事实或触发外部操作。

## 为什么使用来源 ID

模型不生成 URL，而是引用已有的 `issue-42` / `doc-1` 等 ID。每条建议必须引用对应 issue；跨候选引用、未知 ID、重复/遗漏 issue 或无效字段会使分析失败。UI 从事实快照中解析链接。

这只能防止不存在的引用，不能证明模型的推论正确。语义归因仍需要人工标注与评测。

## 为什么保留“待核实”

API 分页限制、网络错误、认领表述差异和标题相似度都会影响判断。例如，相关 PR 可能只是提及 issue，并未解决同一个问题；因此暂缓表示先比较 diff，而不是断言已经有人实现同一修复。

技术相关性、协作状态和政策确认是三个独立维度。`matching.py` 保存词语命中位置、代码块语言、原文路径扩展名和仓库语言的间接证据；扩展名只表明路径的技术线索，不证明文件存在。仓库初选不会自动凑满数量，定向 issue 则始终保留。`references.py` 把作者解决意图、Refs/Related 范围关联、标题相似与普通引用分开。`research.py` 同时检查认领和实现记录；贡献规则始终由 `policy_check` 单独表达。

## 为什么只核实原文路径

`source_hints.py` 只读取 issue 已提及的路径，先把默认分支解析到 commit，再查询 Contents API；不猜目录、不克隆、不执行代码。每候选最多查询两个路径、全报告最多八次文件查询，各候选先共享第一轮查询机会。缺失路径、过时行号、请求失败与预算用完都在报告中保留。

这能给出可点击、可复查的阅读入口，仍不能回答“根因在哪”或“修改是否正确”。`action_plan.py` 根据这些入口、具体 PR 和原文行为生成待办；信息不足就要求定位或补齐复现，不捏造测试命令。

## 为什么模型使用单独的材料投影

界面需要完整来源、文件摘录、行为材料和行动计划。直接把整个报告发给模型会重复发送同一原文，增加延迟与截断风险。`llm.model_input` 只保留有上限的文档、规则和候选来源，记录省略；输出引用针对实际发送的来源校验。这个限制约束输入与引用，不证明语义分析正确，也不替代真实模型评测。

## 为什么先做本地工具

本地使用减少账户系统和云部署的复杂度，便于用户使用自己的 GitHub/模型配置。HTTP 服务仅监听 loopback，限制 Host、同源请求和任务数量；网页只渲染文本与经过验证的 GitHub HTTPS 链接。它尚不是经过安全审计的公网服务。

## 后续扩展应保留的约束

新增模型、缓存、源码搜索或贡献政策解析时，均需保留采集时间、来源、覆盖范围和失败信息。若以后增加实际提交能力，应做成独立的人工审阅流程，不能由 issue 或模型内容直接触发。
